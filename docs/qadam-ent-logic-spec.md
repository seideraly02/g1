# Техническое задание Qadam ENT: логика системы

Это ТЗ описывает бизнес-логику, данные, расчёты и поведение системы. Требования к дизайну здесь не рассматриваются.

## 1. Цель проекта

Разработать платформу для подготовки к ЕНТ, которая:

- определяет примерный уровень ученика;
- формирует персональный план;
- подбирает вопросы по слабым темам;
- возвращает ошибки на повторение;
- сохраняет прогресс;
- работает при временном отсутствии интернета;
- показывает понятную статистику;
- предоставляет весь пользовательский интерфейс и учебный контент только на казахском языке для аудитории Казахстана.

Технологии:

- Vue 3;
- `<script setup lang="ts">`;
- Vite;
- TypeScript;
- Tailwind CSS;
- Pinia;
- Vue Router.

Auth, session, subjects и diagnostic работают через same-origin Netlify Function API и Netlify
Database PostgreSQL. Остальные незавершённые учебные модули могут временно использовать локальные
репозитории, пока для них не определены серверные контракты.

Текущая диагностика получает вопросы через `GET /diagnostic/:subjectId` без правильных ответов,
проверяет и неизменно фиксирует первый выбранный вариант пользователя и `operationId` через
`POST /diagnostic/:subjectId/check` для немедленной обратной связи и сохраняет завершённую попытку идемпотентным
`POST /diagnostic/:subjectId/submit` со стабильным `operationId`.

### 1.1. Язык и аудитория

Qadam предназначен только для казахоязычных учеников Казахстана.

- весь пользовательский интерфейс, учебный контент, системные сообщения, уведомления, accessibility-тексты и отображаемые mock-данные используются только на естественном казахском языке;
- в интерфейсе используется корректная казахская терминология, включая «ҰБТ» вместо русского «ЕНТ»;
- переключатель языка, локализация, русская fallback-версия, Vue I18n и сохраняемое состояние языка отсутствуют;
- сущности хранят одно казахское значение в полях `name`, `text` и `explanation` без locale-суффиксов;
- идентификаторы кода и API остаются на английском языке;
- корневой HTML-документ использует `<html lang="kk">`.

## 3. Основной пользовательский сценарий

```text
Первый запуск
→ регистрация или вход
→ выбор предмета
→ диагностика из 5 вопросов
→ предварительный результат
→ настройка плана
→ ежедневные тренировки
→ результат
→ повторение ошибок
→ обновление аналитики и прогноза
```

При перезапуске приложение должно определить состояние пользователя:

- есть незавершённая диагностика — предложить продолжить;
- диагностика завершена, но план не настроен — открыть настройку плана;
- план настроен — открыть главную;
- есть незавершённая тренировка — показать возможность продолжить;
- сессия истекла — сохранить ответы и создать новую сессию.

## 5. Обязательная регистрация и диагностика

До выбора предмета пользователь обязан создать аккаунт или войти. При регистрации обязательны имя, фамилия, город, номер телефона Казахстана и пароль; подтверждение пароля проверяется только в UI и не отправляется backend. При входе используются телефон и пароль. Пароль хранится только как adaptive BCrypt hash и никогда не возвращается клиенту. Backend создаёт серверную сессию в защищённой `HttpOnly` cookie; auth-токены и профиль не хранятся в `localStorage`. Без действующей сессии учебные маршруты недоступны.

Существующие legacy-аккаунты имеют `password_hash = null`. Повторная регистрация такого номера возвращает conflict: без отдельного доказательства владения номером пароль устанавливать нельзя. Password reset в текущей версии отсутствует и должен быть реализован отдельным безопасным flow. Регистрация ограничивается до выполнения BCrypt по fingerprint телефона и доверенному client fingerprint; вход имеет отдельные failure-only лимиты по тем же измерениям.

### 5.1. Создание

После регистрации создаётся диагностическая сессия. Тип `guest-diagnostic` временно сохраняется как техническое имя существующего формата данных и не означает гостевой доступ.

Диагностика содержит пять уникальных вопросов:

- 2 лёгких;
- 2 средних;
- 1 сложный.

Если вопросов нужной сложности недостаточно, система выбирает доступные вопросы без дублирования.

### 5.2. Ответ

В диагностике:

1. Пользователь выбирает вариант.
2. Ответ сразу сохраняется.
3. Повторное нажатие не изменяет ответ.
4. Варианты блокируются.
5. Показывается правильный ответ и объяснение.
6. Разблокируется переход к следующему вопросу.

### 5.3. Результат

Рассчитываются:

```text
accuracy = correctAnswers / answeredQuestions × 100
```

Показываются:

- правильные ответы;
- неправильные ответы;
- точность;
- затраченное время;
- наиболее успешная тема;
- тема, требующая дополнительной проверки.

Пять вопросов не считаются полноценным прогнозом ЕНТ. Результат обязательно получает статус `preliminary`.

Если данных недостаточно для определения сильной или слабой темы, система выводит состояние «Недостаточно данных».

## 6. Авторизация и прогресс

В MVP используется серверная password-auth с HttpOnly cookie session, описанная в разделе 5.
Диагностика и учебные маршруты доступны только после регистрации или входа. Пользователь переходит к
настройке плана, а дальнейший прогресс сохраняется только через авторизованные серверные операции.

## 7. Настройка персонального плана

Пользователь указывает:

- профильные предметы;
- текущий примерный балл;
- желаемый балл;
- дату ЕНТ;
- ежедневную цель.

Правила валидации:

- должен быть выбран необходимый набор предметов;
- целевой балл не может быть отрицательным;
- дата ЕНТ должна находиться в будущем;
- ежедневная цель: только 10, 20, 30 или 50 вопросов;
- конкретные ограничения ЕНТ должны поступать из конфигурации, а не быть жёстко записаны в компонентах.

После сохранения система рассчитывает:

```text
daysRemaining = examDate - currentDate
estimatedTotalQuestions = dailyGoal × daysRemaining
```

План пересчитывается один раз в день и после значительного изменения результатов.

---

## 8. Формирование плана на день

Количество вопросов равно ежедневной цели пользователя.

Распределение вопросов:

- 40% — ошибки, срок повторения которых наступил;
- 40% — слабые темы;
- 20% — новые или смешанные вопросы.

Если в одной категории недостаточно вопросов, свободные места распределяются между остальными категориями.

Правила подбора:

- один вопрос не повторяется дважды в одной сессии;
- недавно отвеченные вопросы не повторяются в течение 14 дней;
- исключение — вопросы, назначенные на повторение;
- отключённые вопросы не используются;
- предпочтение отдаётся выбранным предметам;
- вопросы должны распределяться между несколькими темами;
- при отсутствии статистики используется равномерный подбор.

Незавершённые вопросы не переносятся механически на следующий день. Новый план формируется заново с учётом актуальных ошибок и слабых тем.

После выполнения дневной цели план получает статус `completed`. Пользователь может запустить дополнительную тренировку, но основной план повторно не создаётся.

## 9. Обычная тренировка

Поддерживаемые режимы:

- план на день;
- тренировка по предмету;
- тренировка по теме;
- смешанная тренировка;
- работа над ошибками;
- быстрая тренировка.

Состояния сессии:

| Состояние | Значение |
|---|---|
| `created` | Сессия создана, но не начата |
| `in-progress` | Есть открытые или отвеченные вопросы |
| `completed` | Пользователь завершил сессию |
| `abandoned` | Пользователь отказался продолжать |
| `expired` | Продолжение сессии невозможно |

Правила:

- до выбора ответа переход дальше запрещён;
- после ответа изменить вариант нельзя;
- ответ сохраняется сразу;
- обновление страницы восстанавливает текущий вопрос;
- время ответа считается только во время активной вкладки;
- при уходе приложения в фон таймер обычной тренировки приостанавливается;
- ответ засчитывается в статистику сразу после фиксации;
- завершение сессии не должно повторно добавлять уже учтённые ответы.

## 10. Работа над ошибками

При неправильном ответе создаётся или обновляется `ReviewItem`.

```ts
interface ReviewItem {
  id: string
  userId: string
  questionId: string
  stage: number
  wrongAnswersCount: number
  consecutiveCorrectAnswers: number
  nextReviewAt: string
  status: 'active' | 'mastered'
}
```

Интервалы повторения:

| Результат повторения | Следующее повторение |
|---|---|
| Неправильно | Через 1 день, этап сбрасывается |
| Первый правильный | Через 3 дня |
| Второй правильный | Через 7 дней |
| Третий правильный | Через 14 дней |
| Четвёртый правильный | Через 30 дней |
| Правильно после финального этапа | Ошибка закреплена |

Правила:

- повторная ошибка не создаёт второй `ReviewItem`;
- неправильный ответ сбрасывает прогресс закрепления;
- закреплённая ошибка остаётся в истории;
- при новой ошибке по этому вопросу она снова становится активной;
- «Все ошибки закреплены» показывается, если активных вопросов для повторения нет.

## 11. Определение слабых и сильных тем

Тема анализируется только после минимум пяти ответов.

Для защиты от случайного результата используется сглаженная точность:

```text
smoothedAccuracy = (correctAnswers + 2) / (totalAnswers + 4)
```

Классификация:

- менее 60% — слабая тема;
- от 60% до 79% — нейтральная;
- 80% и выше — сильная тема.

При одинаковой точности приоритет слабой темы определяется по:

1. количеству ошибок;
2. давности последней тренировки;
3. важности темы;
4. близости даты ЕНТ.

## 12. Результат тренировки

После завершения рассчитываются:

- количество отвеченных вопросов;
- количество правильных;
- количество неправильных;
- точность;
- общее время;
- среднее время ответа;
- результат по темам;
- новые ошибки;
- закреплённые ошибки;
- заработанные рейтинговые очки.

```text
accuracy = correct / answered × 100
averageTime = totalActiveAnswerTime / answered
```

Пропущенные вопросы не входят в `answered`, но учитываются отдельно.

На основании результата система создаёт следующую рекомендацию:

- низкая точность по теме — повторить тему;
- много ошибок, срок которых наступил — разобрать ошибки;
- высокая точность — перейти к более сложным вопросам;
- дневная цель не завершена — продолжить текущий план;
- цель завершена — предложить короткое повторение или отдых.

## 13. Прогноз результата ЕНТ

Прогноз не должен строиться по гостевой диагностике из пяти вопросов.

Уровни достоверности:

- меньше 20 ответов — прогноз не рассчитывается;
- 20–99 ответов — предварительный широкий диапазон;
- 100 и более ответов, минимум по 15 на каждый выбранный предмет — устойчивый прогноз.

Для каждого предмета вычисляется сглаженная точность с повышенным весом свежих ответов:

- последние 30 дней — вес `1`;
- 31–60 дней — вес `0.7`;
- 61–90 дней — вес `0.4`;
- более старые ответы — вес `0.2`.

```text
subjectScore = subjectMaxScore × weightedAccuracy
predictedScore = сумма subjectScore
```

Ширина диапазона:

- предварительный прогноз — ±15% от максимального балла;
- средняя достоверность — ±10%;
- высокая достоверность — ±7%.

Максимальные баллы и структура ЕНТ берутся из конфигурации. Их нельзя жёстко записывать в frontend.

Прогноз является учебной оценкой, а не гарантированным результатом.

## 14. Пробный ЕНТ

Структура пробного теста задаётся через `TrialTemplate`:

```ts
interface TrialTemplate {
  id: string
  version: number
  durationMinutes: number
  subjectRules: {
    subjectId: string
    questionCount: number
    maxScore: number
  }[]
}
```

При старте:

1. Выбирается актуальный шаблон.
2. Создаётся фиксированный список вопросов.
3. Сохраняется версия каждого вопроса.
4. Фиксируется время начала и завершения.
5. Создаётся черновик попытки.

В отличие от обычной тренировки пользователь может:

- переходить между вопросами;
- пропускать вопросы;
- отмечать вопросы;
- изменять ответы до завершения;
- вернуться к пропущенным.

Правильные ответы и объяснения до завершения не показываются.

Таймер:

- продолжает идти при сворачивании приложения;
- не сбрасывается после обновления страницы;
- продолжает идти без интернета;
- автоматически завершает попытку после истечения времени.

Перед досрочным завершением необходимо показать:

- отвеченные;
- пропущенные;
- отмеченные;
- оставшееся время.

После подтверждения ответы блокируются. Повторная отправка результата не создаёт новую попытку.

Если пользователь подтверждает выход из незавершённого пробного ҰБТ, черновик попытки и его ответы удаляются. Такая попытка не участвует в результатах и аналитике, не восстанавливается и не может быть продолжена. После выхода пользователь попадает на `/home`.

## 15. Аналитика

В расчётах не учитываются:

- тестовые mock-сессии разработчика;
- удалённые попытки;
- дубликаты синхронизации;
- ответы, не зафиксированные пользователем.

Рассчитываются:

- точность за 7 и 30 дней;
- количество решённых вопросов;
- среднее и медианное время ответа;
- прогресс по предметам;
- слабые и сильные темы;
- выполнение дневной цели;
- активность по дням;
- прогноз результата;
- количество активных ошибок.

Для скорости используется медиана. Значения меньше 2 секунд и больше 300 секунд помечаются как аномальные и не влияют на среднюю скорость.

Если данных недостаточно, система возвращает отдельное состояние `insufficient-data`, а не нулевой результат.

## 16. Серия занятий

Активный день засчитывается, если пользователь:

- ответил минимум на пять вопросов; или
- завершил одну тренировку по ошибкам.

День определяется по часовому поясу пользователя.

Правила заморозок:

- в начале недели выдаются две бесплатные заморозки;
- остаток не переносится;
- при первом пропуске заморозка применяется автоматически;
- нельзя применить заморозку два пропущенных дня подряд;
- после второго последовательного пропуска серия обнуляется;
- заморозки нельзя покупать;
- дни режима паузы не продлевают и не обнуляют серию.

Офлайн-активность должна быть засчитана по фактическому времени выполнения после синхронизации.

---

## 17. Лиги и рейтинговые очки

Участие добровольное. По умолчанию рейтинг отключён.

Начисление очков:

- зафиксированный ответ — 5 очков;
- правильный ответ — дополнительно 5;
- выполнение дневного плана — 20;
- закрепление ошибки — 10.

Один и тот же вопрос приносит очки не более одного раза за неделю, кроме назначенного интервального повторения.

Каждую неделю:

1. Пользователь попадает в группу из 20–30 участников близкого уровня.
2. Верхняя зона повышается.
3. Средняя зона остаётся.
4. Нижняя зона понижается.

Количество мест в каждой зоне задаётся конфигурацией.

Дополнительные правила:

- отсутствие активности всю неделю понижает на одну лигу;
- ниже стартовой лиги опуститься нельзя;
- режим паузы сохраняет текущую лигу;
- после долгого отсутствия пользователь попадает в группу близкого уровня;
- отключение рейтинга скрывает пользователя из таблиц;
- другим участникам нельзя показывать подробную учебную статистику;
- используются только псевдоним и аватар.

## 18. Уведомления

Типы уведомлений:

- остаток дневной цели;
- готовое интервальное повторение;
- изменение точности;
- новая рекомендация;
- завершение недели лиги;
- результат синхронизации.

Правила:

- не отправлять напоминание, если цель уже выполнена;
- не отправлять напоминания во время режима паузы;
- учитывать часовой пояс;
- одинаковое событие не создаёт два уведомления;
- пользователь может отключить каждый тип;
- прочтение синхронизируется между устройствами;
- максимум два учебных push-уведомления в день.

## 19. Локальное сохранение

В `localStorage` сохраняются:

- `guestId`;
- выбранный предмет;
- гостевая диагностика;
- текущий вопрос;
- ответы;
- гостевой результат;
- настройки плана;
- активная тренировка;
- черновик пробного ЕНТ;
- очередь синхронизации;
- статус синхронизации.

Работа с `localStorage` выполняется только через единый `PersistenceService`. Компоненты не должны обращаться к хранилищу напрямую.

Ключи должны иметь версию:

```text
qadam.settings.v1
qadam.guest.v1
qadam.sessions.v1
qadam.plan.v1
qadam.syncQueue.v1
qadam.auth.v1
```

При изменении формата данных должна выполняться миграция. Повреждённые данные не должны ломать запуск приложения.

Токены авторизации нельзя хранить в `localStorage`.

## 20. Offline и синхронизация

Без интернета пользователь может:

- продолжить уже загруженную тренировку;
- сохранять ответы;
- завершить локальную сессию;
- продолжить пробный ЕНТ;
- просматривать ранее сохранённую статистику.

Каждое локальное изменение добавляется в очередь:

```ts
interface SyncOperation {
  operationId: string
  entityType: string
  entityId: string
  action: 'create' | 'update' | 'complete'
  payload: unknown
  createdAt: string
  attempts: number
  status: 'pending' | 'syncing' | 'synced' | 'error'
}
```

После восстановления сети:

1. Операции отправляются по времени создания.
2. Сервер проверяет `operationId`.
3. Повторная операция возвращает предыдущий результат.
4. Подтверждённая операция удаляется из очереди.
5. Ошибочная операция остаётся для повторной отправки.

При истёкшей авторизации очередь сохраняется, а синхронизация получает статус `auth-required`.

## 21. Архитектура frontend и Pinia-модули

Код организуется по feature и domain-ответственности. Целевое направление зависимостей:

```text
Vue UI → Pinia orchestration → pure domain engines → repository interfaces
```

Правила модульности:

- route views собирают экран, а feature-модули реализуют законченные пользовательские сценарии;
- связанные с feature компоненты, store-код, services, types и tests хранятся рядом; код переносится в `shared` только после появления нескольких реальных потребителей со стабильным контрактом;
- компоненты не выполняют бизнес-расчёты, не обращаются напрямую к `localStorage` и не знают деталей API;
- детерминированные правила реализуются небольшими именованными чистыми функциями без скрытых side effects;
- composable используется только для переиспользуемого реактивного или lifecycle-поведения, но не как оболочка над чистым расчётом;
- универсальные base-компоненты, services, factories и абстракции «на будущее» не создаются;
- props, emits, stores, engines, repositories, persistence payloads и API DTO имеют явные типизированные контракты;
- `unknown` проверяется на внешней границе; `any` не используется без документированной причины;
- циклические зависимости и глубокие unrelated cross-feature imports запрещены;
- repository interfaces принадлежат domain/application-границе, а mock, local и будущие API-реализации остаются взаимозаменяемыми;
- design tokens являются единым источником цветов, типографики, 4 px-based отступов, радиусов, elevation и состояний взаимодействия;
- неиспользуемый код, зависимости, стили, ассеты, дубли и временные generated-файлы удаляются;
- каждый business engine покрывается focused-тестами для обычных случаев, границ, insufficient-data, некорректных входов и idempotency, где это применимо.

Перечисленные ниже stores и services являются целевыми границами ответственности. Пустые файлы и слои заранее не создаются.

Создать следующие stores:

- `authStore` — пользователь и авторизация;
- `settingsStore` — часовой пояс и уведомления;
- `questionStore` — предметы, темы и вопросы;
- `sessionStore` — текущая тренировка;
- `planStore` — персональный и дневной план;
- `reviewStore` — ошибки и интервальные повторения;
- `trialStore` — пробный ЕНТ;
- `analyticsStore` — статистика и прогноз;
- `streakStore` — серия и заморозки;
- `leagueStore` — лига и очки;
- `syncStore` — offline-очередь.

Бизнес-расчёты нельзя размещать внутри Vue-компонентов.

Создать отдельные сервисы:

```text
quizEngine.ts
dailyPlanEngine.ts
reviewScheduler.ts
forecastEngine.ts
analyticsEngine.ts
streakEngine.ts
leagueEngine.ts
syncService.ts
persistenceService.ts
```

## 23. Критерии приёмки логики

Проект считается функционально готовым, если:

- без действующей сессии доступны только welcome и единый экран регистрации/входа;
- при регистрации имя, фамилия, город, телефон Казахстана и пароль обязательны;
- вход принимает телефон и пароль, а ошибка credentials не раскрывает существование номера;
- диагностика всегда содержит пять уникальных вопросов;
- выбранный ответ нельзя изменить после фиксации;
- результат пяти вопросов не называется точным прогнозом;
- обновление страницы не удаляет текущую попытку;
- первый сценарий начинается с выбора предмета и не содержит шага выбора языка;
- весь видимый интерфейс, вопросы, объяснения, ошибки, уведомления, accessibility-тексты и отображаемые fixtures написаны на казахском языке;
- отсутствуют переключатель языка, Vue I18n, locale-state, русская fallback-копия и сохранение языка;
- content-контракты используют `name`, `text` и `explanation` без пар `Ru`/`Kk`;
- в корневом документе задано `<html lang="kk">`;
- пользователь может продолжить незавершённую сессию;
- ошибки автоматически попадают на повторение;
- интервалы повторения рассчитываются корректно;
- дневной план учитывает ошибки и слабые темы;
- один вопрос не дублируется внутри сессии;
- пробный ЕНТ восстанавливается после перезапуска;
- таймер пробного ЕНТ не останавливается в фоне;
- повторная отправка не создаёт дубликаты;
- при ошибке входа введённые данные формы не теряются и пользователь может повторить попытку;
- офлайн-ответ появляется в очереди;
- после восстановления сети очередь синхронизируется;
- прогноз не рассчитывается при недостатке данных;
- серия корректно использует заморозки;
- режим паузы не обнуляет серию и лигу;
- отключённый рейтинг скрывает пользователя;
- вся бизнес-логика находится в stores и сервисах, а не в компонентах;
- engines являются детерминированными чистыми функциями и покрыты focused boundary- и idempotency-тестами;
- реализации repositories заменяются без изменения компонентов и business engines;
- стабильные повторяющиеся правила и UI-паттерны переиспользуются без дублирования;
- отсутствуют неиспользуемый код и ассеты, дубли компонентов, dead routes/actions, placeholders и временные generated-файлы;
- type-check, tests, production build и визуальная проверка на 390 px и широком viewport проходят успешно.
